# Vocabulary and terminology

This guide keeps beginner terminology consistent in the English edition.

| Concept | Preferred wording | Notes |
| --- | --- | --- |
| variable | variable | A value the program can remember/change |
| input | input / answer from the user | Keep `input()` as code |
| output | what the program prints / result | Do not require “output” early |
| condition | condition | Explain as a question that is true or false |
| loop | loop | Use `for` loop and `while` loop |
| function | function | Early explanation: “a named task we can use again” |
| parameter | parameter | Introduce when functions need flexible input |
| return value | value the function sends back | Plain language first |
| list | list | A collection of values |
| index | index / position in the list | Explain explicitly that Python starts at 0 |
| random | random | `random` remains the module name |
| bug | bug / error | Treat as normal debugging work |
| debugging | debugging | Explain through concrete investigation |
| game state | game state | Mainly adult material at first |
| project scope | scope / size of the project | Adult/project-planning term |

## Style rules
- Use short sentences and concrete examples.
- Keep Python keywords/functions in code formatting.
- Prefer “the program” over claims that the computer literally thinks or knows.
- Use “What do you think will happen ...?” consistently for prediction.
- Introduce at most one or two major new ideas per lesson.
- Do not require syntax memorisation.
- Treat error messages as information.
- Use fictional data when real personal information is unnecessary.
- Keep advanced terminology in adult material until useful.
